# Notifications and Blockly – Developer Guide

**Status:** Backend timeout evaluation and two Blockly root variants are implemented; toolbox switching is implemented; end-to-end runtime verification remains in progress.  
**Branch:** `phase_1_foundation`  
**Last reviewed:** 15 November 2026

## 1. Scope and ownership

The dashboard has distinct notification producers. Their ownership boundaries must remain explicit:

- **Blockly notifications** are configured and evaluated by the dashboard's notification engine.
- **External API notifications** are created and managed exclusively by authenticated external clients through the Notifications API.
- **System notifications** are generated by the dashboard itself, for example temporary Quick Action errors.

The dashboard may combine notifications from different producers for presentation. Presentation aggregation does not transfer ownership or management rights between producers.

## 2. Source-code responsibilities

| File | Responsibility |
|---|---|
| `src/server/notifications.ts` | Blockly notification configuration validation, Homey source collection, condition evaluation, and dashboard notification aggregation |
| `src/server/notification-conditions.ts` | Reusable schedule and duration-condition evaluation helpers |
| `src/client/notification-condition-blockly.ts` | Conversion between Blockly blocks and the canonical condition JSON nodes |
| Blockly editor components | Blockly workspace, block definitions, fields, serialization, and user interaction |
| `src/server/notifications-api.ts` | Dedicated storage and lifecycle for external API notifications only |

Do not move Blockly timeout or lifecycle behavior into `notifications-api.ts`.

## 3. Blockly notification data flow

1. The Blockly editor represents the notification's condition tree and user-editable notification content.
2. Blockly serialization converts supported blocks into the canonical notification configuration JSON.
3. The backend validates the configuration and loads enabled notification rules.
4. `notifications.ts` collects the unique Homey device-capability and Logic-variable sources needed by those rules.
5. The backend reads current values from Homey and evaluates each condition tree.
6. The dashboard receives the evaluated Blockly notification states.
7. The dashboard presentation layer combines these with active API notifications. This is a read/presentation integration only.

The backend is the single evaluator. Do not implement a second condition evaluator in Blockly or the browser.

## 4. Canonical Blockly condition model

The evaluator in `notifications.ts` uses the canonical schemaVersion 1 condition tree. Supported node families include:

- Comparison leaves, using a Homey device capability or Logic variable.
- AND/OR groups.
- NOT nodes.
- Duration nodes.
- Schedule nodes.
- Weekday nodes.

The Blockly conversion helpers in `notification-condition-blockly.ts` translate duration blocks to and from duration JSON nodes. A duration condition means that its child condition must remain continuously active for the configured duration before the result becomes active. This is a condition gate, not a notification display timeout.

Reusable time and duration evaluation helpers live in `notification-conditions.ts`. Schedule evaluation supports configured weekdays, local start/end times, overnight intervals, and optional IANA time zones. Duration evaluation tracks the start of a continuously active condition.

## 5. Important distinction: condition duration vs. notification visibility

These are separate concepts and must not be conflated:

- **Condition duration** (existing): how long a condition must remain active before it evaluates as active. It is represented by a `duration` condition node and is part of the condition tree.
- **Notification visibility timeout** (implemented, runtime validation in progress): how long an already-triggered Blockly notification remains visible on the dashboard.

The visibility timeout is selected by choosing a separate `Genereer melding` root block variant. There are two distinct root blocks: one without a timeout and one with a timeout. The timeout variant carries the selected visibility duration as notification behavior; it is not another condition node and must not change the meaning of existing duration blocks.

## 6. Approved Blockly visibility-timeout behavior

The user approved the following behavior on 15 November 2026:

1. When a Blockly notification condition becomes active and triggers the notification, its visibility timer starts.
2. The notification remains visible for the configured duration, even if the underlying condition becomes inactive before the timer expires.
3. If the same notification condition becomes active again while that visibility timer is still running, the original timer is retained.
4. Reactivation does not restart, extend, or otherwise modify the original expiry deadline.
5. The notification therefore expires at the end of the original visibility period.

Example: a 15-minute notification is triggered at 12:00. The condition becomes inactive at 12:03 and active again at 12:08. The notification still expires at 12:15, not 12:23.

This behavior is specific to Blockly notifications. It does not change API notification expiry semantics or the API's storage/lifecycle implementation.

### Two root-block variants

The Blockly editor must provide two distinct `Genereer melding` root blocks:

- **Without timeout:** retains the existing lifecycle. The notification is visible while its condition is active and disappears when that condition becomes inactive.
- **With timeout:** starts the selected visibility timer when the notification is first triggered. The notification remains visible until that original timer expires, regardless of an intervening inactive condition. Reactivation while the timer is running does not restart or extend it.

There is no `Never`/permanent option inside the timeout block. Users who do not want a timeout select the separate root block without timeout.

### Allowed timeout values

The timeout block offers exactly these fixed choices:

- 1 minute
- 2 minutes
- 5 minutes
- 15 minutes
- 30 minutes
- 1 hour
- 2 hours
- 4 hours
- 8 hours
- 12 hours
- 24 hours

Use stable technical duration values (milliseconds) in the serialized configuration; user-facing labels must use the project's i18n resources. Do not add arbitrary free-form durations unless the user approves a change.

## 7. Notifications API boundary

`src/server/notifications-api.ts` is exclusively responsible for external API notifications. It has its own persistent storage file (`DATA_DIR/api-notifications.json`), validation, CRUD operations, optional `expiresAt`, and expiry monitor.

The API's `expiresAt` behavior is not a shared Blockly timeout service. Do not import API creation, patching, deletion, storage, or expiry-monitor behavior into Blockly to implement the approved visibility timeout.

The existing import of `getActiveApiNotifications` in `notifications.ts` is used to read active API notifications for dashboard presentation. It does not make the API module responsible for Blockly evaluation or lifecycle.

The API may only manage its own API-owned records. Blockly configuration and system notifications remain outside the API's ownership boundary.

## 8. Existing runtime considerations

- Blockly condition evaluation and the current duration-condition start tracking are in `notifications.ts` and `notification-conditions.ts`.
- The current duration-condition start tracking uses in-memory state (`durationStartedAt`); it is not persistent across container restarts.
- The dashboard's evaluation response can provide a next evaluation deadline for condition transitions. This is separate from a future notification visibility expiry deadline.
- Blockly visibility timers are intentionally not persistent. A Docker/container restart does not need to restore an in-progress timeout; the in-memory timer state is lost on restart.
- The two root-block variants make the behavior explicit. Existing notifications using the no-timeout behavior retain their current lifecycle.

## 9. Implementation constraints for the visibility timeout

Implementation constraints and verification checklist:

- Keep the implementation in the Blockly notification path, with the relevant configuration/editor conversion on the client and lifecycle/evaluation handling in the Blockly notification backend.
- Keep the visibility timer separate from condition-tree evaluation and from the API expiry monitor.
- Use a stable notification identity so a re-evaluation can find the existing visibility window instead of creating or extending another one.
- Preserve the first trigger's expiry deadline while the visibility window is active.
- Ensure condition becoming inactive does not prematurely hide a notification whose approved visibility window is still active.
- Ensure expiry causes a dashboard refresh at the correct deadline, without requiring an unrelated Homey event.
- Keep the Notifications API module and its exclusive ownership unchanged.
- Add tests for initial activation, early condition deactivation, reactivation without timer reset, expiry, multiple notifications, and existing configurations without the new setting.

The serialized property is `timeoutMs`; the runtime visibility timer is maintained in memory. The user-facing block variants, allowed duration choices, absence of a permanent option in the timeout block, and non-persistent timer behavior are implemented. Do not infer or reuse the API's `expiresAt` contract.
